================================================================================
  数据与接口层 / 并发处理（UML-056，对应 B=56）
================================================================================

  中任务概述：
  充电桩服务端需要同时处理多个客户端连接（多个充电用户 +
  管理端），每个连接可能并发发送请求。本中任务定义服务端
  的多线程并发处理机制，确保多个客户端请求被安全并发处理，
  Qt客户端主界面保持响应，线程资源在连接断开时正确释放。

  组件清单（本中任务涉及）：
  - 服务端主线程（Main Thread，监听新连接）
  - 工作线程池（Worker Thread Pool，处理客户端请求）
  - 线程安全的消息队列（跨线程消息传递）
  - 互斥锁（Mutex，保护共享资源）
  - 客户端Socket管理器（服务端侧，每个连接一个实例）

  解耦设计：
  - 并发处理是服务端内部机制，对客户端透明——客户端不感知
    服务端是单线程还是多线程
  - 每个客户端连接分配独立的工作线程，线程间通过消息队列
    和互斥锁通信，不共享业务状态
  - 数据库访问通过DAL层的事务机制保证并发安全（UML-053）
  - Qt客户端的主线程（UI线程）不执行网络IO和数据库操作，
    通过信号槽机制在工作线程中处理后通知UI线程

  与已有两个系统的兼容关系：
  充电用户端（多个并发）─→ 服务端工作线程1 ─→ DAL（互斥锁保护）
  充电用户端（多个并发）─→ 服务端工作线程2 ─→ DAL（互斥锁保护）
  PC运营管理端          ─→ 服务端工作线程3 ─→ DAL（互斥锁保护）
                                    ↑
                          SQLite（单写者模型，天然串行化写操作）


------------------------------------------------------------
【UML-056】多线程服务
------------------------------------------------------------

■ 场景
  服务端启动后，主线程监听TCP端口。当多个充电用户端和PC运营
  管理端同时连接时，服务端为每个连接创建或分配工作线程，
  并发处理各客户端的请求。工作线程调用各领域服务和DAL完成
  业务处理，通过消息队列将响应回传给客户端。

  典型并发场景：
  - 场景1：两个用户同时预约同一个空闲充电桩
    → 两个工作线程同时调用 pile_update_status(idle→reserved)
    → 乐观锁保证只有一个成功，另一个返回失败
  - 场景2：用户正在充电时，管理员查看经营看板
    → 充电用户的工作线程推送 CHARGE_UPDATE
    → 管理端的工作线程查询聚合统计数据
    → 读操作并发无冲突
  - 场景3：用户充电结算时，管理员冻结该用户
    → 结算事务（更新订单+扣余额+桩状态）在事务内
    → 冻结操作（更新status）在不同事务
    → SQLite单写者模型保证两个事务串行执行，不冲突

■ 参与者
  - 服务端主线程（监听连接，分发到工作线程）
  - 工作线程池（处理客户端请求的业务逻辑）
  - 客户端Socket管理器（服务端侧，每个连接一个）
  - 消息分发器（在工作线程中执行，路由消息到领域服务）
  - 各领域服务（用户服务、站点服务、充电服务、订单服务、管理端服务）
  - 数据访问层 DAL（通过事务和乐观锁保证并发安全）

■ 前置条件
  - 服务端已启动，主线程已绑定监听端口
  - 线程池已初始化（默认最大线程数 = 20）

■ 处理流程
  1. 服务端主线程 → 服务端主线程：创建 QTcpServer，监听端口 8888
  2. 服务端主线程 → 服务端主线程：初始化线程池
     （最大线程数 = 20，空闲线程复用，无空闲时创建新线程
      达到上限则排队等待）
  3. loop 服务端运行期间
     - 服务端主线程 → 服务端主线程：等待新连接（QTcpServer::nextPendingConnection）
     - alt 有新客户端连接
       - 服务端主线程 → 客户端Socket管理器：创建服务端侧
         Socket管理器实例，绑定 client_id，连接 readyRead 信号
       - 服务端主线程 → 工作线程池：分配一个工作线程
         处理该连接的消息
       - 工作线程 → 工作线程：进入消息接收循环
     end
  end

  4. （工作线程处理客户端消息）
  5. loop 工作线程消息循环
     - 工作线程 → 客户端Socket管理器：等待消息到达
       （通过条件变量或信号槽机制阻塞）
     - alt 有消息到达
       - 客户端Socket管理器 → 工作线程：通知消息到达，
         传递 recv_buffer
       - 工作线程 → 消息编解码器：调用 parse_all_messages(recv_buffer)
         解析所有完整消息
       - loop 遍历解析出的消息
         - 消息编解码器 → 消息分发器：传递 (msg_type, payload)
         - 消息分发器 → 消息分发器：根据 msg_type 路由到领域服务
         - alt 查询类消息（LOGIN_REQ, QUERY_STATIONS_REQ, ADMIN_QUERY_REQ 等）
           - 消息分发器 → 领域服务：调用对应查询方法
           - 领域服务 → DAL：调用 DAL 查询方法（只读，无锁冲突）
           - DAL → 领域服务：返回查询结果
           - 领域服务 → 消息分发器：构造响应消息
           - 消息分发器 → 客户端Socket管理器：发送响应
         else 写入类消息（RESERVE_REQ, END_CHARGE_REQ, ADMIN_ACTION_REQ 等）
           - 消息分发器 → 领域服务：调用对应业务方法
           - 领域服务 → DAL：在事务中执行写入操作
             （dal_begin_transaction → 多步操作 → dal_commit/rollback）
           - alt 事务成功
             - DAL → 领域服务：返回成功
             - 领域服务 → 消息分发器：构造成功响应
           else 事务失败（乐观锁冲突或数据库异常）
             - DAL → 领域服务：返回失败，事务已回滚
             - 领域服务 → 消息分发器：构造错误响应
           end
           - 消息分发器 → 客户端Socket管理器：发送响应
         end
       end
     end
  end

  6. alt 客户端断开连接
     - 客户端Socket管理器 → 工作线程：检测连接断开
       （Socket error 或 disconnected 信号）
     - 工作线程 → 工作线程：清理该连接的资源：
       - 注销 client_id
       - 清空 recv_buffer
       - 通知会话管理器清除该连接的会话信息（如有）
     - 工作线程 → 工作线程池：归还线程到空闲池，等待分配新连接
   else 服务端关闭
     - 服务端主线程 → 工作线程池：通知所有工作线程退出
     - 工作线程池 → 各工作线程：发送退出信号
     - 各工作线程 → 各工作线程：完成当前消息处理后退出
     - 服务端主线程 → 服务端主线程：等待所有线程结束（join），
       关闭 QTcpServer，释放资源
  end

■ 线程安全机制
  1. SQLite 数据库访问：
     - SQLite 在 WAL 模式下支持多读单写
     - 配置 PRAGMA journal_mode = WAL
     - 配置 PRAGMA busy_timeout = 5000（写冲突时等待5秒）
     - DAL 层的乐观锁（old_status 参数）保证状态变更的并发安全
     - DAL 层的事务（BEGIN/COMMIT/ROLLBACK）保证多步操作的原子性

  2. 共享资源保护：
     - 会话管理器（session_map）：互斥锁保护
       多个线程可能同时读写会话映射表（登录时写入、心跳时读取、
       冻结时删除），通过 QMutex 保护
     - 消息队列：线程安全的 QQueue + QMutex + QWaitCondition
       工作线程从队列取消息，主线程向队列投递消息

  3. Qt客户端UI线程安全：
     - 充电用户端和管理端都是 Qt GUI 应用，主线程是UI线程
     - 网络IO在单独的QThread中执行，不阻塞UI
     - 工作线程通过信号槽（queued connection）通知UI线程更新界面
     - 禁止在工作线程中直接操作UI控件

  4. 充电模拟的定时推送：
     - 充电中的用户由充电服务维护一个定时器（每3秒推送一次
       CHARGE_UPDATE），该定时器在工作线程中运行
     - 多个用户同时充电时，多个定时器并发运行，互不影响
     - 定时器通过 DAL 读取当前充电量，推送更新消息

■ 资源释放规则
  - 连接断开时：
    - 清空 recv_buffer
    - 注销 client_id 和会话信息
    - 如有充电定时器，停止定时器
    - 归还工作线程到线程池
  - 服务端关闭时：
    - 停止接受新连接
    - 等待所有活跃连接完成当前消息处理（最多等待5秒）
    - 强制断开超时连接
    - 关闭数据库连接
    - 销毁线程池

■ 并发冲突场景分析
  场景1：两个用户同时预约同一个桩（idle）
    - 线程1：pile_update_status(pile_id, 'reserved', 'idle')
      → UPDATE ... WHERE status='idle' → 影响行数1 → 成功
    - 线程2：pile_update_status(pile_id, 'reserved', 'idle')
      → UPDATE ... WHERE status='idle' → 影响行数0（已被线程1改）
      → 返回失败 → 上层返回"充电桩已被预约"
    - 结果：只有一个用户预约成功，数据一致

  场景2：用户充电结算时管理员冻结该用户
    - 线程1（充电服务）：结算事务
      BEGIN → order_settle + pile_update_status + user_update_balance → COMMIT
    - 线程2（管理端服务）：冻结操作
      BEGIN → user_update_status → COMMIT
    - SQLite单写者模型：两个事务串行执行，不会交错
    - 结果：先执行的事务先提交，后执行的事务读到最新数据

  场景3：多个用户同时查询附近充电站
    - 多个线程同时执行 SELECT 查询
    - WAL模式支持多读并发，无锁等待
    - 结果：所有查询并发执行，无冲突

■ 输出
  - 多客户端并发请求被安全处理，互不干扰
  - Qt客户端UI线程保持响应，不卡顿
  - 资源在连接断开时正确释放，无内存泄漏
  - 并发冲突通过乐观锁和事务机制安全解决

■ 关联
  - 前序：UML-054（连接建立后才有消息需处理）、UML-055（消息解码后分发）
  - 后续：所有上层消息（UML-010~046）都在工作线程中处理
  - 依赖：UML-053（事务机制保证写操作并发安全）
  - 兼容性：
    - 充电用户端和PC运营管理端的请求在服务端统一通过工作线程处理
    - 用户端请求和管理端请求可能并发到达（如用户充电时管理员看板）
    - 并发处理对两个客户端都透明，客户端不感知服务端线程模型
  - 性能：
    - 线程池上限20，超过20个并发连接时排队等待
    - 典型场景：10个用户 + 1个管理端 = 11个连接，线程池充足
    - SQLite的WAL模式优化了读并发性能
