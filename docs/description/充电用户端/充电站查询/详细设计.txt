================================================================================
  充电用户端 / 充电站查询（UML-018 ~ UML-022，对应 B=18~22）
================================================================================

  中任务概述：
  用户在首页点击"找桩"入口，通过下拉选择区域或手动输入地址进行
  定位（模拟GPS），系统调用腾讯地图API将地址转为经纬度，然后
  按距离由近及远展示周边充电站列表（卡片形式），点击某站点可
  查看该站所有充电桩的详细信息。这是充电流程的前置环节——
  用户通过此模块找到并选定目标充电站和充电桩。

  组件清单（本中任务涉及）：
  - 用户（actor）
  - 充电站列表界面（QT 列表页，含定位输入、站点卡片列表）
  - 充电站详情界面（QT 详情页，展示站内充电桩列表）
  - 站点服务（服务端，处理充电站和充电桩查询）
  - 充电站表（charging_stations）
  - 充电桩表（charging_piles）
  - 腾讯地图API（外部Web API，地址转经纬度）
  - 用户端全局状态（提供登录态校验）

  解耦设计：
  - 站点服务独立于用户服务和充电服务，只负责查询站点/桩信息
  - 腾讯地图API调用封装在站点服务内，用户端不直接调用外部API
  - 充电站详情查询返回的桩列表数据，可被 UML-026（选择空闲充电桩）
    直接使用，两个中任务通过数据传递而非直接调用实现耦合


------------------------------------------------------------
【UML-018】位置输入与模拟定位
------------------------------------------------------------

■ 场景
  用户在首页点击"找桩"或"附近充电站"入口，进入充电站列表界面。
  由于本项目在Linux桌面运行，无法使用真实GPS，因此采用"模拟定位"：
  用户通过下拉列表选择预设区域（如"海淀区""朝阳区"），或在输入框
  中手动输入地址文本。输入完成后，系统将地址文本发送到服务端，
  进入 UML-019（地址转经纬度）流程。

■ 参与者
  - 用户（actor）
  - 充电站列表界面
  - 用户端全局状态

■ 前置条件
  - 用户已登录（UML-013）

■ 处理流程
  1. 用户 → 充电站列表界面：点击首页"找桩"入口
  2. 充电站列表界面 → 用户端全局状态：校验登录态
  3. 用户端全局状态 → 充电站列表界面：返回 logged_in = true
  4. 充电站列表界面 → 用户：渲染定位输入区域：
     - 下拉列表：预设区域选项（如"海淀区""朝阳区""东城区"等）
     - 手动输入框：可输入任意地址文本
     - "搜索"按钮
  5. alt 用户从下拉列表选择区域
     - 用户 → 充电站列表界面：选择某个预设区域
     - 充电站列表界面 → 充电站列表界面：将选中区域名作为地址文本，
       标记定位输入完成
     - （控制流转入 UML-019 地址转经纬度）
   else 用户手动输入地址
     - 用户 → 充电站列表界面：在输入框中输入地址文本，点击"搜索"
     - 充电站列表界面 → 充电站列表界面：校验输入非空
     - alt 输入非空
       - 充电站列表界面 → 充电站列表界面：标记定位输入完成
       - （控制流转入 UML-019 地址转经纬度）
     else 输入为空
       - 充电站列表界面 → 用户：提示"请选择区域或输入地址"
     end
  end

■ 输出
  - 成功：获得地址文本（区域名或手动输入的地址），传入 UML-019
  - 失败：提示用户重新输入

■ 关联
  - 前序：UML-013（登录状态维护）
  - 后续：UML-019（地址转经纬度）
  - 说明：本步骤是纯前端交互，不产生网络请求


------------------------------------------------------------
【UML-019】地址转经纬度
------------------------------------------------------------

■ 场景
  UML-018 获得地址文本后，用户端将地址发送到服务端，服务端
  调用腾讯地图Web API将地址文本转换为经纬度坐标。转换后的
  坐标用于后续的充电站距离计算和排序。如果地址无法解析
  （如地址文本无意义），服务端返回错误，用户端提示重新输入。

■ 参与者
  - 充电站列表界面
  - 站点服务
  - 腾讯地图API（外部Web API）

■ 前置条件
  - UML-018 已获得地址文本

■ 处理流程
  1. 充电站列表界面 → 站点服务：发送 GEOCODE_REQ { address: "地址文本" }
  2. 站点服务 → 腾讯地图API：发起HTTP请求
     GET https://apis.map.qq.com/ws/geocoder/v1/?address={地址文本}&key={API_KEY}
  3. alt 地理编码成功
     - 腾讯地图API → 站点服务：返回
       { status: 0, result: { location: { lng: 经度, lat: 纬度 } } }
     - 站点服务 → 站点服务：提取经纬度坐标 (longitude, latitude)
     - 站点服务 → 充电站列表界面：返回 GEOCODE_RESP
       { success: true, longitude: 经度, latitude: 纬度 }
     - （控制流转入 UML-020 按距离排序）
   else 地址无法解析
     - 腾讯地图API → 站点服务：返回 { status: 非零 } 或 result 为空
     - 站点服务 → 充电站列表界面：返回 GEOCODE_RESP
       { success: false, error: "地址无法识别" }
     - 充电站列表界面 → 用户：提示"地址无法识别，请重新输入或选择区域"
     - 充电站列表界面 → 充电站列表界面：返回定位输入状态，用户可重新输入
   else 网络请求失败（腾讯API不可达）
     - 站点服务 → 充电站列表界面：返回 GEOCODE_RESP
       { success: false, error: "地图服务暂不可用" }
     - 充电站列表界面 → 用户：提示"地图服务暂不可用，请稍后重试"
  end

■ 输出
  - 成功：获得用户位置的经纬度坐标 (longitude, latitude)，传入 UML-020
  - 失败：提示用户重新输入地址

■ 关联
  - 前序：UML-018（位置输入与模拟定位）
  - 后续：UML-020（按距离排序）
  - 外部依赖：腾讯地图Web API（地理编码接口）
  - 说明：API调用封装在服务端，用户端不直接调用腾讯API。
    这样做的好处是API Key不暴露在客户端，且服务端可做缓存。


------------------------------------------------------------
【UML-020】按距离排序
------------------------------------------------------------

■ 场景
  获得用户经纬度后，服务端查询数据库中所有充电站，计算每个站到
  用户位置的距离（Haversine公式），按距离升序排列，返回排好序的
  充电站列表。列表中每个站点包含：站名、充电单价、总桩数、空闲桩数、
  距离（公里）。此步骤是 UML-019（地址转经纬度）和 UML-021
  （充电站卡片）之间的服务端处理环节。

■ 参与者
  - 充电站列表界面
  - 站点服务
  - 充电站表（charging_stations）
  - 充电桩表（charging_piles）

■ 前置条件
  - UML-019 已返回用户经纬度 (longitude, latitude)

■ 处理流程
  1. 充电站列表界面 → 站点服务：发送 QUERY_STATIONS_REQ
     { longitude, latitude }
  2. 站点服务 → 充电站表：SELECT station_id, station_name, address,
     longitude, latitude, price_per_kwh FROM charging_stations
  3. 充电站表 → 站点服务：返回所有站点记录
  4. 站点服务 → 充电桩表：对每个站点查询桩统计
     SELECT COUNT(*) AS total, SUM(CASE WHEN status='idle' THEN 1 ELSE 0 END)
     AS idle_count FROM charging_piles WHERE station_id = ?
  5. 充电桩表 → 站点服务：返回每个站点的总桩数和空闲桩数
  6. 站点服务 → 站点服务：对每个站点计算距离：
     使用 Haversine 公式计算用户经纬度与站点经纬度间的球面距离
     distance = haversine(user_lat, user_lng, station_lat, station_lng)
     单位：公里
  7. 站点服务 → 站点服务：按 distance 升序排序站点列表
  8. 站点服务 → 充电站列表界面：返回 QUERY_STATIONS_RESP
     { stations: [
       { station_id, station_name, address, price_per_kwh,
         total_piles, idle_count, distance_km },
       ... (按距离升序)
     ] }
  9. alt 查询结果非空
     - （控制流转入 UML-021 充电站卡片）
   else 无充电站数据
     - 站点服务 → 充电站列表界面：返回空列表
     - 充电站列表界面 → 用户：显示"附近暂无充电站"
  end

■ 输出
  - 成功：返回按距离升序排列的充电站列表（含站名、价格、桩数、距离）
  - 空结果：提示附近暂无充电站

■ 关联
  - 前序：UML-019（地址转经纬度）
  - 后续：UML-021（充电站卡片）
  - 数据：SELECT charging_stations 全表，SELECT charging_piles 按 station_id 聚合
  - 说明：距离计算在服务端完成，避免客户端拿到所有站点数据后本地计算。
    Haversine 公式：a = sin²(Δφ/2) + cos(φ₁)·cos(φ₂)·sin²(Δλ/2);
    c = 2·atan2(√a, √(1−a)); d = R·c （R=6371km）


------------------------------------------------------------
【UML-021】充电站卡片
------------------------------------------------------------

■ 场景
  UML-020 返回排好序的充电站列表后，用户端将列表渲染为卡片形式。
  每张卡片显示：站名、充电价格（元/度）、电桩总数/空闲数量、
  距离（公里）。卡片按距离由近及远垂直排列。用户点击某张卡片的
  距离信息可进入导航（UML-023），点击卡片其他区域可查看站点详情
  （UML-022）。

■ 参与者
  - 用户（actor）
  - 充电站列表界面

■ 前置条件
  - UML-020 已返回充电站列表数据

■ 处理流程
  1. 充电站列表界面 → 充电站列表界面：接收 QUERY_STATIONS_RESP 中的
     stations 数组
  2. 充电站列表界面 → 充电站列表界面：遍历 stations 数组，为每个站点
     创建一个卡片 UI 组件（QFrame 或自定义 Widget）：
     - 顶部行：站名（加粗），右侧显示距离"X.XX km"（可点击，样式
       类似链接，鼠标悬停变色）
     - 中间行：充电价格"¥X.XX/度"
     - 底部行：桩数信息"空闲 X / 总共 X"（空闲数为0时标红显示）
  3. 充电站列表界面 → 用户：渲染卡片列表，卡片从上到下按距离升序排列
  4. alt 用户点击卡片距离信息
     - 用户 → 充电站列表界面：点击某卡片的距离区域
     - 充电站列表界面 → 充电站列表界面：记录目标站点的 station_id,
       address, longitude, latitude
     - （控制流转入 UML-023 加载腾讯地图）
   else 用户点击卡片其他区域
     - 用户 → 充电站列表界面：点击某卡片
     - 充电站列表界面 → 充电站列表界面：记录目标站点的 station_id
     - （控制流转入 UML-022 充电站详情）
   else 用户返回首页
     - 用户 → 充电站列表界面：点击返回按钮
     - 充电站列表界面 → 用户端首页：返回首页
  end

■ 输出
  - 卡片列表渲染完成，用户可选择查看详情或导航

■ 关联
  - 前序：UML-020（按距离排序）
  - 后续：UML-022（充电站详情）、UML-023（加载腾讯地图，导航）
  - 说明：本步骤是纯前端渲染，不产生网络请求。卡片数据来自
    UML-020 的响应。空闲桩数为0的卡片应视觉提示"暂无空闲"


------------------------------------------------------------
【UML-022】充电站详情
------------------------------------------------------------

■ 场景
  用户在充电站列表（UML-021）中点击某站点卡片，进入充电站详情页。
  详情页展示该站点的基本信息（地址、充电单价、在线率）和站内所有
  充电桩的列表（编号、类型、状态、功率）。用户可在此页面选择
  空闲充电桩（转入 UML-026 选择空闲充电桩）。

■ 参与者
  - 用户（actor）
  - 充电站详情界面
  - 站点服务
  - 充电桩表（charging_piles）

■ 前置条件
  - UML-021 中用户点击了某站点卡片，已获得 station_id

■ 处理流程
  1. 充电站列表界面 → 充电站详情界面：传递 station_id，
     切换到详情页面
  2. 充电站详情界面 → 站点服务：发送 QUERY_PILES_REQ { station_id }
  3. 站点服务 → 充电桩表：SELECT pile_id, pile_number, pile_type,
     power_kw, status FROM charging_piles WHERE station_id = ?
  4. 充电桩表 → 站点服务：返回该站所有充电桩记录
  5. 站点服务 → 站点服务：计算统计信息：
     total = 桩总数
     idle = status='idle' 的数量
     in_use = status='in_use' 的数量
     fault = status='fault' 的数量
     online_rate = (idle + in_use) / total × 100%
  6. 站点服务 → 充电站详情界面：返回 QUERY_PILES_RESP
     { station_id, piles: [
       { pile_id, pile_number, pile_type, power_kw, status },
       ...
     ], stats: { total, idle, in_use, fault, online_rate } }
  7. 充电站详情界面 → 充电站详情界面：渲染详情页面：
     - 顶部信息区：
       站名（从列表页传入）
       地址
       充电单价"¥X.XX/度"
       在线率"XX.X%"
     - 桩列表区：每行显示
       桩编号 | 类型（快充/慢充标签） | 功率"XX kW" | 状态标签
       状态标签颜色：idle=绿色"空闲" / in_use=蓝色"使用中" /
       reserved=黄色"已预约" / fault=红色"故障"
     - idle 状态的桩行可点击（有"选择"按钮），其他状态不可点击
  8. alt 用户点击某空闲桩的"选择"按钮
     - 用户 → 充电站详情界面：点击 idle 状态桩的"选择"
     - 充电站详情界面 → 充电站详情界面：记录选中的 pile_id,
       pile_number, power_kw
     - （控制流转入 UML-026 选择空闲充电桩 → UML-027 预约充电）
   else 用户点击非空闲桩
     - 充电站详情界面 → 用户：该桩行显示提示"该桩当前不可用"，
       不可点击
   else 用户返回列表
     - 用户 → 充电站详情界面：点击返回
     - 充电站详情界面 → 充电站列表界面：返回站点列表
  end

■ 输出
  - 充电站详情页展示站信息和所有充电桩状态
  - 用户可选择空闲桩进入充电流程

■ 关联
  - 前序：UML-021（充电站卡片，提供 station_id）
  - 后续：UML-026（选择空闲充电桩）→ UML-027（预约充电）
  - 数据：SELECT charging_piles WHERE station_id = ?
  - 说明：此页面是充电站查询与充电流程的衔接点——用户在此选定
    目标充电桩，数据传递到充电流程模块
