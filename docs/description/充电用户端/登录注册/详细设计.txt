================================================================================
  充电用户端 / 登录注册（UML-010 ~ UML-013，对应 B=10~13）
================================================================================

  中任务概述：
  用户打开程序 → 输入手机号 → 格式校验 → 登录或自动注册 → 维护登录态。
  这是用户端的入口模块，后续所有操作都依赖此模块建立的登录态。

  组件清单（本中任务涉及）：
  - 用户（actor）
  - 登录界面（QT 登录页，含手机号输入框和登录按钮）
  - 用户服务（服务端，处理登录/注册请求）
  - 用户表（users，SQLite）
  - 用户端全局状态（维护 session_id 和 user_info）

  解耦设计：
  - 登录注册模块只负责建立登录态，不涉及其他业务逻辑
  - 登录态通过"用户端全局状态"传递给其他模块，模块间不直接耦合
  - 用户服务是唯一的服务端入口，其他模块通过各自的领域服务访问服务端


------------------------------------------------------------
【UML-010】手机号格式验证
------------------------------------------------------------

■ 场景
  用户点击应用图标打开程序，进入登录界面。在输入框中键入手机号
  并点击"登录"按钮时，系统首先对手机号进行格式校验。这是整个
  用户端流程的第一步——只有格式合法的手机号才会被提交到服务端
  查询，格式不合法则直接拦截在前端。

■ 参与者
  - 用户（actor）
  - 登录界面（用户端 QT 界面，含手机号输入框和登录按钮）

■ 前置条件
  - 应用已启动，登录界面已渲染完成
  - 用户端已与服务端建立 Socket 连接（应用启动时自动连接）

■ 处理流程
  1. 用户 → 登录界面：在输入框中键入手机号，点击"登录"按钮
  2. 登录界面 → 登录界面：读取输入框文本，执行格式校验：
     - 非空检查：输入不能为空字符串
     - 长度检查：必须恰好 11 位
     - 正则匹配：必须匹配 1[3-9][0-9]{9}（第一位为1，第二位为3-9，
       后9位为0-9，共11位大陆手机号）
  3. alt 手机号格式合法
     - 登录界面 → 登录界面：标记校验通过，进入 UML-011（已存在用户登录）
       或 UML-012（新用户自动注册）流程——具体走哪个分支由服务端查询结果决定
     - 登录界面 → 登录界面：禁用登录按钮（防止重复提交），显示"正在登录..."
   else 输入为空
     - 登录界面 → 用户：弹窗提示"请输入手机号"，停留在登录页，输入框获焦
   else 位数不正确（非11位）
     - 登录界面 → 用户：弹窗提示"请输入11位手机号"，停留在登录页
   else 格式不匹配（含非法字符或号段不对）
     - 登录界面 → 用户：弹窗提示"手机号格式不正确，请检查后重新输入"，
       清空输入框，停留在登录页
  end

■ 输出
  - 成功：格式校验通过，控制流转入服务端查询流程（UML-011/UML-012）
  - 失败：弹窗提示具体原因，用户停留在登录页可重新输入

■ 关联
  - 前序：无（这是用户端入口的第一步）
  - 后续：UML-011（已存在用户登录）、UML-012（新用户自动注册）
  - 说明：本步骤是纯前端校验，不产生网络请求，目的是在前端拦截
    明显非法的输入，避免无意义的服务端查询


------------------------------------------------------------
【UML-011】已存在用户登录
------------------------------------------------------------

■ 场景
  手机号格式校验通过后（UML-010），用户端向服务端发送登录请求。
  服务端查询用户表，发现该手机号已注册——即用户已存在。此时
  服务端返回用户完整信息（ID、昵称、头像路径、钱包余额），
  用户端保存登录态并跳转到首页。这是"免密登录"机制的核心：
  只要手机号在用户表中存在，即视为验证通过，无需密码。

■ 参与者
  - 用户（actor）
  - 登录界面
  - 用户服务（服务端业务逻辑层，处理用户登录/注册请求）
  - 用户表（users）

■ 前置条件
  - UML-010 手机号格式校验已通过
  - Socket 连接已建立

■ 处理流程
  1. 登录界面 → 用户服务：发送 LOGIN_REQ { phone: "用户输入的手机号" }
  2. 用户服务 → 用户表：查询 phone = 输入手机号 AND status = 'normal' 的记录
  3. alt 用户存在且状态为 normal
     - 用户表 → 用户服务：返回匹配的用户记录
       （user_id, phone, nickname, avatar_path, balance, register_time, status）
     - 用户服务 → 用户服务：构造用户信息对象，生成会话标识 session_id
     - 用户服务 → 登录界面：返回 LOGIN_RESP
       { success: true, user_info: { user_id, nickname, avatar_path, balance,
         session_id } }
     - 登录界面 → 登录界面：保存 user_info 和 session_id 到用户端全局状态
     - 登录界面 → 登录界面：切换到用户端首页，加载首页组件
     - 登录界面 → 用户：首页渲染完成，在页面顶部弹出"登录成功"提示，
       提示3秒后自动消失
     - （控制流转入 UML-013 登录状态维护）
   else 用户存在但状态为 frozen（被冻结）
     - 用户表 → 用户服务：返回用户记录（status = 'frozen'）
     - 用户服务 → 登录界面：返回 LOGIN_RESP
       { success: false, error: "账号已被冻结，请联系管理员" }
     - 登录界面 → 用户：弹窗提示"账号已被冻结，请联系管理员"，停留在登录页
   else 用户不存在（手机号未注册）
     - 用户表 → 用户服务：无匹配记录
     - 用户服务 → 登录界面：返回 LOGIN_RESP
       { success: false, error: "user_not_found" }
     - 登录界面 → 登录界面：识别 error = "user_not_found"，
       控制流转入 UML-012（新用户自动注册）
  end

■ 输出
  - 成功（用户存在且 normal）：进入用户端首页，显示登录成功提示，
    用户端全局状态保存登录态
  - 被冻结：弹窗提示，停留登录页
  - 不存在：转入 UML-012 新用户自动注册流程

■ 关联
  - 前序：UML-010（手机号格式验证）
  - 后续：UML-013（登录状态维护）、UML-012（新用户自动注册，当用户不存在时）
  - 数据：读取 users 表，不修改数据
  - 业务规则：免密登录——手机号即身份，无需密码。冻结用户无法登录。


------------------------------------------------------------
【UML-012】新用户自动注册
------------------------------------------------------------

■ 场景
  UML-011 中服务端查询用户表发现手机号不存在，用户端识别到
  "user_not_found"错误。此时系统不要求用户填写注册信息，而是
  自动以该手机号创建新用户：默认昵称为"用户+手机号后4位"，
  默认头像为灰色占位图，初始余额为0.00元。注册完成后即视为
  登录成功，直接进入首页。这种"首次登录即注册"的设计降低了
  使用门槛——用户无需经历独立的注册步骤。

■ 参与者
  - 用户（actor）
  - 登录界面
  - 用户服务
  - 用户表（users）

■ 前置条件
  - UML-011 已返回 user_not_found
  - 手机号格式已校验通过（UML-010）

■ 处理流程
  1. 登录界面 → 用户服务：发送 REGISTER_REQ（复用 LOGIN_REQ，附加
     is_auto_register: true 标识）{ phone, is_auto_register: true }
  2. 用户服务 → 用户服务：构造新用户数据：
     - phone = 输入的手机号
     - nickname = "用户" + 手机号后4位（如 13800138000 → "用户8000"）
     - avatar_path = 默认灰色头像路径
     - balance = 0.00
     - register_time = 当前时间
     - status = 'normal'
  3. 用户服务 → 用户表：INSERT 新用户记录
  4. alt 插入成功
     - 用户表 → 用户服务：返回新插入的 user_id
     - 用户服务 → 用户服务：生成 session_id，构造用户信息对象
     - 用户服务 → 登录界面：返回 LOGIN_RESP
       { success: true, user_info: { user_id, nickname, avatar_path,
         balance: 0.00, session_id }, is_new_user: true }
     - 登录界面 → 登录界面：保存 user_info 和 session_id 到用户端全局状态
     - 登录界面 → 登录界面：切换到用户端首页
     - 登录界面 → 用户：首页渲染完成，弹出"注册成功，欢迎加入！"
       提示（区别于 UML-011 的"登录成功"），3秒后自动消失
     - （控制流转入 UML-013 登录状态维护）
   else 插入失败（如手机号已被并发注册——极端并发场景）
     - 用户表 → 用户服务：返回唯一约束冲突错误
     - 用户服务 → 用户服务：改为查询该手机号（可能另一线程已插入）
     - 用户服务 → 用户表：SELECT ... WHERE phone = ?
     - 用户表 → 用户服务：返回已存在的用户记录
     - 用户服务 → 登录界面：返回 LOGIN_RESP（同 UML-011 成功路径）
     - 登录界面 → 用户：正常进入首页
   else 数据库写入失败
     - 用户表 → 用户服务：返回数据库错误
     - 用户服务 → 登录界面：返回 LOGIN_RESP
       { success: false, error: "注册失败，请稍后重试" }
     - 登录界面 → 用户：弹窗提示"注册失败，请稍后重试"，停留在登录页
  end

■ 输出
  - 成功：新用户创建并直接登录，进入首页，显示"注册成功"提示
  - 并发冲突（他人已注册同号）：转为正常登录流程
  - 数据库失败：弹窗提示，停留登录页

■ 关联
  - 前序：UML-011（已存在用户登录，返回 user_not_found）
  - 后续：UML-013（登录状态维护）
  - 数据：写入 users 表（INSERT）
  - 业务规则：自动注册不收集额外信息，默认昵称"用户+后4位"，
    初始余额0.00元，默认灰色头像


------------------------------------------------------------
【UML-013】登录状态维护
------------------------------------------------------------

■ 场景
  用户通过 UML-011 或 UML-012 成功登录后，用户端需要维护登录态。
  登录态包括：当前用户信息（user_id、昵称、头像、余额）和会话
  标识（session_id）。这些信息保存在用户端本地内存中（用户端全局
  状态），在应用的生命周期内持续有效。登录态的用途：
  1）作为后续所有操作的请求参数（如预约充电需要 user_id）
  2）首页展示用户信息（昵称、头像、余额）
  3）判断用户是否已登录，未登录时拦截需要鉴权的操作
  本任务描述的是登录态的"维护机制"而非一次具体操作——它是一个
  持续生效的状态管理过程。

■ 参与者
  - 用户（actor）
  - 用户端首页（登录后的主界面）
  - 用户端全局状态（应用级单例，维护 session_id 和 user_info）
  - 用户服务

■ 前置条件
  - UML-011 或 UML-012 已成功登录
  - 用户端全局状态已保存 user_info 和 session_id

■ 处理流程
  登录成功后，用户端执行以下状态维护操作：

  1. 登录界面 → 用户端首页：传递 user_info 对象（含 user_id, nickname,
     avatar_path, balance, session_id）
  2. 用户端首页 → 用户端全局状态：存入 user_info，标记 logged_in = true
  3. 用户端首页 → 用户端首页：渲染首页 UI：
     - 顶部显示头像（加载 avatar_path 指向的图片，如无则显示默认灰色头像）
     - 显示昵称文本
     - 显示钱包余额（格式：¥XX.XX）
  4. 用户端首页 → 用户服务：发送 HEARTBEAT { session_id }（可选，
     定时发送心跳包维持服务端会话）
  5. loop 用户使用期间
     - 用户执行任何需要鉴权的操作（找桩、充电、充值等）时
     - 用户端首页 → 用户端全局状态：检查 logged_in == true 且 session_id 非空
     - alt 已登录
       - 用户端全局状态 → 用户端首页：返回 true，继续执行请求，
         在请求参数中附带 session_id 和 user_id
     else 未登录（会话过期或异常退出）
       - 用户端全局状态 → 用户端首页：返回 false
       - 用户端首页 → 用户：弹窗提示"登录已过期，请重新登录"
       - 用户端首页 → 登录界面：跳转到登录界面，用户端全局状态清除本地登录态
     end
  6. alt 用户主动退出（点击退出按钮）
     - 用户 → 用户端首页：点击"退出登录"
     - 用户端首页 → 用户服务：发送 LOGOUT_REQ { session_id }
     - 用户服务 → 用户服务：清除服务端会话记录
     - 用户服务 → 用户端首页：返回 LOGOUT_RESP { success: true }
     - 用户端首页 → 用户端全局状态：清除 user_info 和 session_id，
       logged_in = false
     - 用户端首页 → 登录界面：跳转到登录界面
   else 应用正常关闭
     - 用户端首页 → 用户服务：Socket 断开（应用关闭时自动断开）
     - 用户服务 → 用户服务：检测到连接断开，清除该 session_id 的
       服务端会话记录
     - （下次启动需重新登录，因为登录态不持久化到磁盘）
  end

■ 输出
  - 登录态在应用运行期间持续有效，为所有后续操作提供身份凭证
  - 退出或关闭应用后，登录态清除，下次需重新登录

■ 关联
  - 前序：UML-011（已存在用户登录）、UML-012（新用户自动注册）
  - 后续：充电用户端所有功能（UML-014~033）均依赖此登录态
  - 数据：不直接读写数据库，仅维护本地内存中的会话状态
  - 说明：本任务是一个持续状态而非一次性操作。UML 时序图应体现
    "登录态建立→使用期间持续校验→退出时清除"的完整生命周期
