================================================================================
  充电用户端 / 用户信息（UML-014 ~ UML-017，对应 B=14~17）
================================================================================

  中任务概述：
  用户登录后，可在个人信息页面查看头像/昵称/余额，并支持更换头像、
  修改昵称、钱包充值三项操作。所有操作通过用户服务完成，修改后
  同步更新用户端全局状态中的 user_info。

  组件清单（本中任务涉及）：
  - 用户（actor）
  - 个人信息界面（QT 个人信息页，含头像展示、昵称编辑、余额充值入口）
  - 用户服务（服务端，处理用户信息查询和修改）
  - 用户表（users）
  - 用户端全局状态（维护 user_info，登录态来自 UML-013）

  解耦设计：
  - 个人信息界面不直接访问数据库，所有数据操作经用户服务
  - 修改成功后，用户端全局状态中的 user_info 同步更新，其他模块
    读取到的始终是最新的用户信息
  - 钱包充值只更新 balance 字段，不涉及订单/充电桩等其他表


------------------------------------------------------------
【UML-014】个人信息展示
------------------------------------------------------------

■ 场景
  用户登录后进入首页，点击头像或"个人中心"入口，进入个人信息
  页面。页面展示用户头像、昵称、钱包余额三项信息。这些信息在
  登录时已缓存在用户端全局状态中，因此首屏渲染无需请求服务端；
  但用户可能在外部修改过数据（如在管理端被充值），因此提供
  "刷新"按钮从服务端拉取最新数据。

■ 参与者
  - 用户（actor）
  - 个人信息界面
  - 用户端全局状态
  - 用户服务
  - 用户表（users）

■ 前置条件
  - 用户已登录（UML-013 登录状态维护已建立）
  - 用户端全局状态中持有 user_info（含 user_id, nickname, avatar_path, balance）

■ 处理流程
  1. 用户 → 个人信息界面：点击"个人中心"入口
  2. 个人信息界面 → 用户端全局状态：读取 user_info
  3. 用户端全局状态 → 个人信息界面：返回 { user_id, nickname, avatar_path, balance }
  4. 个人信息界面 → 个人信息界面：渲染页面：
     - 头像区域：加载 avatar_path 指向的图片文件；若文件不存在或路径为空，
       显示默认灰色占位头像
     - 昵称区域：显示 nickname 文本，旁边有"编辑"图标
     - 余额区域：显示 balance，格式"¥XX.XX"，旁边有"充值"按钮
  5. alt 用户点击"刷新"按钮（可选，拉取最新数据）
     - 个人信息界面 → 用户服务：发送 USER_INFO_REQ { user_id, session_id }
     - 用户服务 → 用户表：SELECT user_id, nickname, avatar_path, balance, status
       FROM users WHERE user_id = ?
     - 用户表 → 用户服务：返回用户记录
     - 用户服务 → 个人信息界面：返回 USER_INFO_RESP { nickname, avatar_path, balance }
     - 个人信息界面 → 用户端全局状态：更新 user_info 中的对应字段
     - 个人信息界面 → 个人信息界面：用最新数据重新渲染头像/昵称/余额
   else 刷新失败
     - 个人信息界面 → 用户：显示"刷新失败，显示的是缓存数据"
  end

■ 输出
  - 个人信息页面展示头像、昵称、余额
  - 刷新成功时数据与服务端一致

■ 关联
  - 前序：UML-013（登录状态维护，提供 user_info）
  - 后续：UML-015（更换头像）、UML-016（修改昵称）、UML-017（钱包充值）
  - 数据：首次展示读全局状态（不查库）；刷新时 SELECT users 表
  - 说明：管理端冻结用户后（UML-045），此页面刷新时可能返回
    status='frozen'，用户端应弹窗提示并退出登录


------------------------------------------------------------
【UML-015】更换头像
------------------------------------------------------------

■ 场景
  用户在个人信息页面点击头像区域或"更换头像"按钮，系统弹出
  本地文件选择对话框。用户选择一张图片后，用户端将图片文件
  上传到服务端，服务端将图片保存到服务器文件系统（固定目录），
  并更新用户表中的 avatar_path 字段。更换成功后，用户端全局
  状态和界面同步更新头像显示。

■ 参与者
  - 用户（actor）
  - 个人信息界面
  - 用户服务
  - 用户表（users）

■ 前置条件
  - 用户已登录，个人信息页面已打开（UML-014）

■ 处理流程
  1. 用户 → 个人信息界面：点击"更换头像"按钮
  2. 个人信息界面 → 个人信息界面：弹出本地文件选择对话框
     （QFileDialog，过滤图片格式：*.jpg *.png *.jpeg）
  3. alt 用户选择了图片文件
     - 个人信息界面 → 个人信息界面：读取选中图片文件到内存
     - 个人信息界面 → 用户服务：发送 USER_UPDATE_REQ
       { user_id, field: "avatar", session_id, file_data: <图片二进制> }
     - 用户服务 → 用户服务：生成头像文件存储路径：
       avatars/{user_id}_{timestamp}.jpg
     - 用户服务 → 用户服务：将图片写入服务器文件系统
     - 用户服务 → 用户表：UPDATE users SET avatar_path = ?
       WHERE user_id = ?
     - 用户表 → 用户服务：返回更新成功
     - 用户服务 → 个人信息界面：返回 USER_UPDATE_RESP
       { success: true, new_avatar_path: "avatars/{user_id}_{timestamp}.jpg" }
     - 个人信息界面 → 用户端全局状态：更新 user_info.avatar_path
     - 个人信息界面 → 个人信息界面：重新加载头像图片，界面刷新
     - 个人信息界面 → 用户：头像区域显示新图片，底部短暂提示"更换成功"
   else 用户取消选择
     - 个人信息界面 → 个人信息界面：关闭文件对话框，不做任何操作
   else 图片格式不支持或文件损坏
     - 个人信息界面 → 用户：弹窗提示"不支持的图片格式，请选择JPG或PNG"
   else 服务端保存失败
     - 用户服务 → 个人信息界面：返回 USER_UPDATE_RESP
       { success: false, error: "头像上传失败" }
     - 个人信息界面 → 用户：弹窗提示"头像更换失败，请稍后重试"
  end

■ 输出
  - 成功：用户表 avatar_path 更新，界面显示新头像
  - 失败：弹窗提示原因，头像不变

■ 关联
  - 前序：UML-014（个人信息展示，页面已打开）
  - 后续：无直接后续，但用户端全局状态更新后其他展示头像的地方同步刷新
  - 数据：UPDATE users.avatar_path


------------------------------------------------------------
【UML-016】修改昵称
------------------------------------------------------------

■ 场景
  用户在个人信息页面点击昵称旁的"编辑"图标，弹出昵称编辑对话框，
  输入新昵称后点击保存。系统在客户端校验昵称格式（长度、敏感词），
  校验通过后发送到服务端更新用户表。修改成功后用户端全局状态
  和界面同步更新。

■ 参与者
  - 用户（actor）
  - 个人信息界面
  - 用户服务
  - 用户表（users）

■ 前置条件
  - 用户已登录，个人信息页面已打开（UML-014）

■ 处理流程
  1. 用户 → 个人信息界面：点击昵称旁"编辑"图标
  2. 个人信息界面 → 用户：弹出昵称编辑对话框，预填当前昵称
  3. 用户 → 个人信息界面：输入新昵称，点击"保存"
  4. 个人信息界面 → 个人信息界面：客户端校验：
     - 非空：昵称不能为空字符串
     - 长度：1~20 个字符
     - 字符集：允许中文、英文、数字、下划线
  5. alt 客户端校验通过
     - 个人信息界面 → 用户服务：发送 USER_UPDATE_REQ
       { user_id, field: "nickname", value: "新昵称", session_id }
     - 用户服务 → 用户服务：服务端再次校验（防止绕过客户端校验）：
       长度1~20、字符集合法
     - 用户服务 → 用户表：UPDATE users SET nickname = ?
       WHERE user_id = ?
     - 用户表 → 用户服务：返回更新成功
     - 用户服务 → 个人信息界面：返回 USER_UPDATE_RESP { success: true }
     - 个人信息界面 → 用户端全局状态：更新 user_info.nickname
     - 个人信息界面 → 个人信息界面：昵称区域刷新为新值
     - 个人信息界面 → 用户：底部短暂提示"昵称修改成功"
   else 昵称为空
     - 个人信息界面 → 用户：对话框内提示"昵称不能为空"
   else 昵称过长
     - 个人信息界面 → 用户：对话框内提示"昵称不能超过20个字符"
   else 含非法字符
     - 个人信息界面 → 用户：对话框内提示"昵称只能包含中文、英文、数字和下划线"
   else 服务端校验或写入失败
     - 用户服务 → 个人信息界面：返回 USER_UPDATE_RESP
       { success: false, error: "修改失败" }
     - 个人信息界面 → 用户：弹窗提示"昵称修改失败，请稍后重试"
  end

■ 输出
  - 成功：用户表 nickname 更新，界面显示新昵称
  - 失败：对话框/弹窗提示原因，昵称不变

■ 关联
  - 前序：UML-014（个人信息展示）
  - 数据：UPDATE users.nickname


------------------------------------------------------------
【UML-017】钱包充值
------------------------------------------------------------

■ 场景
  用户在个人信息页面点击"充值"按钮，弹出充值对话框，输入充值
  金额后点击"确认充值"。系统校验金额合法性，发送充值请求到
  服务端。服务端在用户表中增加 balance 字段值（模拟支付成功），
  返回新余额。用户端全局状态和界面同步更新。
  注意：本项目"模拟支付"——不接入真实支付网关，点击充值即
  视为支付成功，直接增加余额。

■ 参与者
  - 用户（actor）
  - 个人信息界面
  - 用户服务
  - 用户表（users）

■ 前置条件
  - 用户已登录，个人信息页面已打开（UML-014）
  - 用户余额来自用户端全局状态中的 balance

■ 处理流程
  1. 用户 → 个人信息界面：点击"充值"按钮
  2. 个人信息界面 → 用户：弹出充值对话框，含金额输入框和"确认充值"按钮
  3. 用户 → 个人信息界面：输入充值金额，点击"确认充值"
  4. 个人信息界面 → 个人信息界面：客户端校验：
     - 非空：金额不能为空
     - 数值合法：必须为正数，最多2位小数
     - 范围：0.01 ~ 9999.99 元
  5. alt 客户端校验通过
     - 个人信息界面 → 用户服务：发送 RECHARGE_REQ
       { user_id, amount: 充值金额, session_id }
     - 用户服务 → 用户服务：再次校验金额合法性（防止绕过客户端）
     - 用户服务 → 用户表：UPDATE users SET balance = balance + ?
       WHERE user_id = ?（在事务中执行）
     - 用户表 → 用户服务：返回更新成功
     - 用户服务 → 用户表：SELECT balance FROM users WHERE user_id = ?
     - 用户表 → 用户服务：返回最新余额
     - 用户服务 → 个人信息界面：返回 RECHARGE_RESP
       { success: true, new_balance: 更新后的余额 }
     - 个人信息界面 → 用户端全局状态：更新 user_info.balance
     - 个人信息界面 → 个人信息界面：余额区域刷新为新值
     - 个人信息界面 → 用户：弹窗提示"充值成功，当前余额 ¥XX.XX"
   else 金额为空
     - 个人信息界面 → 用户：对话框内提示"请输入充值金额"
   else 金额非正数或格式错误
     - 个人信息界面 → 用户：对话框内提示"请输入正确的金额"
   else 金额超出范围
     - 个人信息界面 → 用户：对话框内提示"充值金额需在0.01~9999.99元之间"
   else 服务端写入失败
     - 用户服务 → 个人信息界面：返回 RECHARGE_RESP
       { success: false, error: "充值失败" }
     - 个人信息界面 → 用户：弹窗提示"充值失败，请稍后重试"
  end

■ 输出
  - 成功：用户表 balance 增加，界面显示新余额
  - 失败：弹窗提示原因，余额不变

■ 关联
  - 前序：UML-014（个人信息展示）
  - 后续：UML-031（结束与结算）——充电结算时需要扣减余额，
    余额不足时需要提示用户充值
  - 数据：UPDATE users.balance（增加），SELECT users.balance
  - 业务规则：模拟支付，不接入真实支付网关。充值金额直接加到余额上。
    使用数据库事务确保余额更新原子性。
