================================================================================
  PC运营管理端 / 用户管理（UML-043 ~ UML-045，对应 B=43~45）
================================================================================

  中任务概述：
  管理员从左侧导航栏进入"用户管理"页面。此模块提供充电用户
  的列表浏览、手机号模糊查询和冻结/解冻操作：
    1）用户列表（UML-043）：展示所有注册用户的信息（用户ID、
       手机号、昵称、钱包余额、注册时间、账号状态），默认按
       注册时间倒序排列
    2）手机号模糊查询（UML-044）：管理员在搜索框中输入手机号
       片段（如前3位、后4位），系统模糊匹配返回符合条件的用户
    3）冻结与解冻（UML-045）：管理员将用户状态在 normal 和
       frozen 之间切换——冻结用户无法登录，解冻后恢复正常

  组件清单（本中任务涉及）：
  - 管理员（actor）
  - 用户管理界面（列表页，含搜索框、表格、操作按钮）
  - 管理端服务
  - 用户表（users）
  - 管理端全局状态（提供 admin_id 和 session_id）

  解耦设计：
  - 用户管理是"读+操作"模块，列表和查询只读，冻结/解冻修改
    users 表的 status 字段
  - 冻结/解冻操作只修改用户状态，不涉及用户的其他数据（余额、
    昵称等不变）——状态变更与用户数据解耦
  - 与用户端登录（UML-010~013）的关系：冻结用户在 UML-011
    登录时被拦截，返回"账号已被冻结"提示；解冻后可正常登录
  - 管理端用户管理与用户端用户信息模块完全独立——管理端
    只做状态管理，不修改用户的昵称、头像等个人信息


------------------------------------------------------------
【UML-043】用户列表
------------------------------------------------------------

■ 场景
  管理员从左侧导航栏进入"用户管理"页面。页面加载后展示全量
  注册用户的列表，以表格形式呈现。每行显示一个用户的基本信息：
  用户ID、手机号、昵称、钱包余额、注册时间、账号状态。表格
  上方有搜索框（用于 UML-044 手机号模糊查询）。状态为 normal
  的用户行显示"冻结"按钮，状态为 frozen 的用户行显示"解冻"按钮。

■ 参与者
  - 管理员（actor）
  - 用户管理界面
  - 管理端服务
  - 用户表（users）

■ 前置条件
  - UML-034 管理员登录已完成，管理端全局状态保存了 admin_id 和 session_id

■ 处理流程
  1. 管理员 → 用户管理界面：点击左侧导航栏"用户管理"菜单
  2. 用户管理界面 → 用户管理界面：渲染页面框架，搜索框默认为空，
     表格区域显示"加载中..."
  3. 用户管理界面 → 管理端服务：发送 ADMIN_QUERY_REQ
     { type: "user_list", params: { keyword: null }, session_id }
  4. 管理端服务 → 管理端服务：校验 session_id 有效性
  5. alt session_id 有效
     - 管理端服务 → 用户表：查询全量用户
       SELECT user_id, phone, nickname, balance,
              register_time, status
       FROM users
       ORDER BY register_time DESC
     - 用户表 → 管理端服务：返回全量用户记录列表
     - 管理端服务 → 用户管理界面：返回 ADMIN_QUERY_RESP
       { type: "user_list",
         data: [ { user_id, phone, nickname, balance,
                   register_time, status }, ... ] }
     - 用户管理界面 → 用户管理界面：渲染表格：
       - 列1：用户ID（user_id）
       - 列2：手机号（phone，显示为 138****8000 格式，中间4位脱敏）
       - 列3：昵称（nickname）
       - 列4：钱包余额（balance，格式 ¥XX.XX）
       - 列5：注册时间（register_time，格式 YYYY-MM-DD HH:MM）
       - 列6：账号状态（status，normal→正常/绿色，
         frozen→已冻结/红色）
       - 列7：操作列
         - status=normal → 显示"冻结"按钮
         - status=frozen → 显示"解冻"按钮
     - 用户管理界面 → 管理员：表格渲染完成
   else session_id 无效
     - （处理同 UML-035，跳转登录页）
   else 查询异常
     - 用户管理界面 → 管理员：表格区域显示"数据加载失败，请重试"
  end

■ 输出
  - 成功：表格展示全量用户列表，按注册时间倒序，各行有操作按钮
  - 失败：表格区域显示错误提示

■ 关联
  - 前序：UML-034（管理员登录）
  - 后续：UML-044（手机号模糊查询，在搜索框输入触发）、
    UML-045（冻结/解冻，从操作按钮触发）
  - 数据：读取 users 表（SELECT），不修改数据
  - 业务规则：
    - 按注册时间倒序排列（最新注册的用户在最上方）
    - 手机号中间4位脱敏显示（保护用户隐私）
    - 根据状态显示不同的操作按钮（冻结或解冻）


------------------------------------------------------------
【UML-044】手机号模糊查询
------------------------------------------------------------

■ 场景
  管理员在用户管理页面（UML-043）的搜索框中输入手机号片段
  （如"138"、"8000"、"1380013"等），系统实时模糊匹配手机号
  包含该片段的用户，并在表格中展示查询结果。清空搜索框则
  恢复展示全量用户列表。

■ 参与者
  - 管理员（actor）
  - 用户管理界面
  - 管理端服务
  - 用户表（users）

■ 前置条件
  - UML-034 管理员登录已完成
  - UML-043 用户列表已加载

■ 处理流程
  1. 管理员 → 用户管理界面：在搜索框中输入手机号片段（如"138"）
  2. 用户管理界面 → 用户管理界面：输入框内容变化，
     延迟300ms防抖后触发查询（避免每次按键都发请求）
  3. alt 搜索框为空
     - 用户管理界面 → 用户管理界面：恢复展示 UML-043 加载的
       全量用户列表，不发送新请求
   else 搜索框有内容
     - 用户管理界面 → 管理端服务：发送 ADMIN_QUERY_REQ
       { type: "user_list",
         params: { keyword: "输入的手机号片段" },
         session_id }
     - 管理端服务 → 管理端服务：校验 session_id 有效性
     - alt session_id 有效
       - 管理端服务 → 用户表：模糊查询
         SELECT user_id, phone, nickname, balance,
                register_time, status
         FROM users
         WHERE phone LIKE '%输入片段%'
         ORDER BY register_time DESC
       - 用户表 → 管理端服务：返回匹配的用户记录列表
       - 管理端服务 → 用户管理界面：返回 ADMIN_QUERY_RESP
         { type: "user_list",
           data: [ ...匹配的用户记录 ] }
       - 用户管理界面 → 用户管理界面：重新渲染表格，
         只显示匹配的用户
       - 用户管理界面 → 管理员：表格上方显示"找到 N 条匹配结果"
     else session_id 无效
       - （处理同 UML-035，跳转登录页）
     end
  end

  4. alt 无匹配结果
     - 管理端服务 → 用户管理界面：返回空列表
     - 用户管理界面 → 管理员：表格显示"未找到匹配的用户，
       请检查手机号片段后重试"

■ 输出
  - 有匹配：表格显示匹配的用户列表，上方显示结果数量
  - 无匹配：表格显示"未找到匹配用户"提示
  - 搜索框清空：恢复全量列表

■ 关联
  - 前序：UML-043（用户列表，搜索功能依附于列表页面）
  - 后续：UML-045（冻结/解冻，查询结果中的操作按钮触发）
  - 数据：读取 users 表（LIKE 模糊查询），不修改数据
  - 业务规则：
    - 使用 LIKE '%keyword%' 进行包含匹配
    - 防抖处理（300ms），避免频繁请求
    - 匹配手机号字段（phone），不匹配昵称等其他字段
    - 清空搜索框恢复全量列表，不保留筛选状态


------------------------------------------------------------
【UML-045】冻结与解冻
------------------------------------------------------------

■ 场景
  管理员在用户列表（UML-043 或 UML-044 查询结果）中，对某个
  用户执行冻结或解冻操作。点击"冻结"按钮将正常用户状态改为
  frozen（冻结），点击"解冻"按钮将冻结用户状态改为 normal
  （正常）。冻结后，该用户在用户端登录时（UML-011）会被拦截，
  返回"账号已被冻结"提示，无法使用充电服务。

■ 参与者
  - 管理员（actor）
  - 用户管理界面
  - 管理端服务
  - 用户表（users）

■ 前置条件
  - UML-034 管理员登录已完成
  - UML-043 用户列表已加载，目标用户在列表中

■ 处理流程
  1. alt 管理员点击"冻结"按钮（目标用户 status=normal）
     - 管理员 → 用户管理界面：点击目标用户行的"冻结"按钮
     - 用户管理界面 → 管理员：弹出确认对话框
       "确认冻结用户 [手机号脱敏] [昵称]？冻结后该用户将无法登录"
     - alt 管理员点击"确认"
       - 用户管理界面 → 用户管理界面：禁用按钮，显示"处理中..."
       - 用户管理界面 → 管理端服务：发送 ADMIN_ACTION_REQ
         { type: "freeze_user",
           params: { user_id: 目标用户ID, action: "freeze" },
           session_id }
       - 管理端服务 → 管理端服务：校验 session_id 有效性
       - alt session_id 有效
         - 管理端服务 → 用户表：查询目标用户当前状态
           SELECT status FROM users WHERE user_id = ?
         - alt 目标用户状态为 normal
           - 管理端服务 → 用户表：更新状态为 frozen
             UPDATE users SET status = 'frozen'
             WHERE user_id = ? AND status = 'normal'
           - 用户表 → 管理端服务：返回受影响行数 = 1（更新成功）
           - 管理端服务 → 管理端服务：记录操作日志
             （管理员ID、操作类型=freeze_user、用户ID、操作时间）
           - 管理端服务 → 管理端服务：清除该用户的服务端会话
             （如有活跃会话，使其立即生效）
           - 管理端服务 → 用户管理界面：返回 ADMIN_ACTION_RESP
             { success: true, message: "用户已冻结" }
           - 用户管理界面 → 用户管理界面：刷新列表，
             该用户状态从"正常/绿色"变为"已冻结/红色"，
             操作按钮从"冻结"变为"解冻"
           - 用户管理界面 → 管理员：弹出提示
             "用户 [昵称] 已冻结，该用户将无法登录"
         else 目标用户状态不是 normal（可能已被其他管理员冻结）
           - 管理端服务 → 用户管理界面：返回 ADMIN_ACTION_RESP
             { success: false, error: "该用户当前状态无法执行冻结" }
           - 用户管理界面 → 管理员：提示"该用户已处于冻结状态"
           - 用户管理界面 → 用户管理界面：刷新列表，显示最新状态
         end
       else session_id 无效
         - （处理同 UML-035，跳转登录页）
       end
     else 管理员点击"取消"
       - 用户管理界面 → 用户管理界面：关闭确认对话框，不执行操作
     end

   else 管理员点击"解冻"按钮（目标用户 status=frozen）
     - 管理员 → 用户管理界面：点击目标用户行的"解冻"按钮
     - 用户管理界面 → 管理员：弹出确认对话框
       "确认解冻用户 [手机号脱敏] [昵称]？解冻后该用户可正常登录"
     - alt 管理员点击"确认"
       - 用户管理界面 → 用户管理界面：禁用按钮，显示"处理中..."
       - 用户管理界面 → 管理端服务：发送 ADMIN_ACTION_REQ
         { type: "freeze_user",
           params: { user_id: 目标用户ID, action: "unfreeze" },
           session_id }
       - 管理端服务 → 管理端服务：校验 session_id 有效性
       - alt session_id 有效
         - 管理端服务 → 用户表：查询目标用户当前状态
           SELECT status FROM users WHERE user_id = ?
         - alt 目标用户状态为 frozen
           - 管理端服务 → 用户表：更新状态为 normal
             UPDATE users SET status = 'normal'
             WHERE user_id = ? AND status = 'frozen'
           - 用户表 → 管理端服务：返回受影响行数 = 1（更新成功）
           - 管理端服务 → 管理端服务：记录操作日志
             （管理员ID、操作类型=unfreeze_user、用户ID、操作时间）
           - 管理端服务 → 用户管理界面：返回 ADMIN_ACTION_RESP
             { success: true, message: "用户已解冻" }
           - 用户管理界面 → 用户管理界面：刷新列表，
             该用户状态从"已冻结/红色"变为"正常/绿色"，
             操作按钮从"解冻"变为"冻结"
           - 用户管理界面 → 管理员：弹出提示
             "用户 [昵称] 已解冻，可正常登录"
         else 目标用户状态不是 frozen
           - 管理端服务 → 用户管理界面：返回 ADMIN_ACTION_RESP
             { success: false, error: "该用户当前状态无需解冻" }
           - 用户管理界面 → 管理员：提示"该用户已处于正常状态"
           - 用户管理界面 → 用户管理界面：刷新列表
         end
       else session_id 无效
         - （处理同 UML-035，跳转登录页）
       end
     else 管理员点击"取消"
       - 用户管理界面 → 用户管理界面：关闭确认对话框
     end
  end

■ 输出
  - 冻结成功：用户状态从 normal 变为 frozen，按钮从"冻结"变为"解冻"
  - 解冻成功：用户状态从 frozen 变为 normal，按钮从"解冻"变为"冻结"
  - 状态不符：提示当前状态无需操作，列表刷新
  - 取消：不执行任何操作

■ 关联
  - 前序：UML-043（用户列表）或 UML-044（模糊查询结果中的操作按钮）
  - 后续：无直接后续（列表自动刷新）
  - 数据：读取并修改 users 表（SELECT + UPDATE status 字段）
  - 业务规则：
    - 冻结操作：normal → frozen
    - 解冻操作：frozen → normal
    - 操作前需管理员确认，防止误操作
    - 冻结时清除该用户的服务端会话（如有活跃登录态，立即失效）
    - 操作日志记录管理员ID、操作类型、目标用户ID、操作时间
  - 跨系统影响：
    - 冻结后，用户端登录（UML-011）返回"账号已被冻结，请联系管理员"
    - 冻结后，用户端所有需鉴权的操作（充电、充值等）被拦截
    - 解冻后，用户端可正常登录和使用
    - 冻结/解冻实时生效，不需要用户端重新连接


------------------------------------------------------------
  用户管理与用户端登录状态机的关系
------------------------------------------------------------

  用户状态机：
    normal(正常) ──管理员冻结──→ frozen(冻结) ──管理员解冻──→ normal(正常)

  与用户端登录的关系：
  - normal 状态的用户可正常登录（UML-011 已存在用户登录）
  - frozen 状态的用户登录时被拦截（UML-011 返回"账号已被冻结"）
  - 已登录的用户被冻结时，服务端清除其会话，
    用户端下次操作时检测到登录过期（UML-013 登录状态维护的
    "未登录"分支），跳转回登录页
  - 解冻后用户需重新登录（之前的会话已被清除）

  用户管理模块只管理状态（normal/frozen），不涉及：
  - 用户个人信息修改（由用户端 UML-014~017 处理）
  - 用户余额修改（由用户端充值 UML-016 处理）
  - 用户订单管理（由管理端 UML-046 订单管理查看）
